# Zasm — визуализатор двух-/однопроходного ассемблера
## План реализации на Kotlin + JavaFX

Источник задания: `docs/labs/img.png`, `img_1.png` (текст методички) и `img_2.jpg…img_7.jpg`
(скриншоты примера-эталона «Zasm 1.0/2.0/3.0», Delphi, Зыкин А.А., гр. 4408, 1999 —
приведены методичкой **как иллюстрация UI/workflow**, а не как код для копирования;
конкретный набор команд и мелкие детали студент выбирает сам).

## 0. Что требуется по методичке (сжатая выжимка)

Программа моделирует работу двухпроходного ассемблера тремя нарастающими этапами:

| Этап | Формат объектного модуля | Ключевая новая способность |
|---|---|---|
| 1 | Абсолютный | Базовый проход 1 → ТСИ/вспом. таблица, проход 2 → бинарный код |
| 2 | Перемещаемый | Таблица настройки (relocation) для прямой/относительной адресации |
| 3 | Полный перемещаемый (раздельное ассемблирование) | `EXTDEF`/`EXTREF`, внешние имена/ссылки, сохранение в файл |

Всегда одна форма с 3 панелями:

- **Левая**: исходный текст (редактируемая сетка) + поле адреса загрузки + ТКО (таблица кодов операций, тоже сетка).
- **Средняя**: вспомогательная таблица (результат прохода 1) + ТСИ + список ошибок прохода 1.
- **Правая**: заголовок объектного модуля + список/сетка перемещений (появляется в Этапе 2) + внешние имена (Этап 3) + двоичный код + ошибки прохода 2 (+ кнопка «Сохранить…» в Этапе 3).

Кнопки «Первый проход» / «Второй проход» запускаются последовательно с блокировкой второй до успешного выполнения первой; выпадающий список «Выбор примера» переключает встроенные тестовые программы (в т.ч. с ошибками).

## 1. Технологический стек

- **Kotlin JVM** (2.x) + **JavaFX** через плагин `org.openjfx.javafxplugin`.

## 2. Архитектура

Чёткое разделение **движка** (чистый Kotlin, без зависимостей от JavaFX, легко тестируется) и **UI** (JavaFX, только отображение/события):

```
org.slavacom.zasm
├── model/          — доменные классы (Instruction, SourceLine, SymbolTableEntry, ...)
├── engine/         — Pass1Engine, Pass2Engine, AssemblerEngine, ErrorReporter
├── samples/        — встроенные тестовые программы (для ComboBox "Выбор примера")
├── io/             — сохранение объектного кода в текстовый файл (Этап 3)
└── ui/             — MainApp (Application), панели, table-адаптеры, контроллер
```

`AssemblerEngine` — единственная точка входа для UI: держит текущее состояние
(источник, ТКО, адрес загрузки) и по вызову `runPass1()` / `runPass2()` возвращает
неизменяемый результат (`Pass1Result` / `Pass2Result`) со всеми таблицами и списком ошибок.
UI только рендерит эти результаты в `TableView` — никакой бизнес-логики в контроллерах.

Это позволяет писать unit-тесты на движок (проверка каждого этапа методички —
«проверить работоспособность кода для нескольких примеров, в т.ч. при наличии ошибок»)
без запуска JavaFX.

## 3. Модель предметной области (общая для всех этапов)

### 3.1 Таблица кодов операций (ТКО) — 8 команд по умолчанию

Реконструкция набора команд из скриншотов (коды и длины совпадают с примером,
что даёт согласованную схему адресации — суффикс **N** = относительная адресация,
без суффикса = прямая; это ровно то, что требуется проверить в Этапе 2):

| Мнемоника | Код | Формат (байты) | Длина | Адресация |
|---|---|---|---|---|
| `LD`    | 01 | opcode+reg+addr(4) | 6 | прямая (нужна настройка) |
| `LDN`   | 02 | opcode+reg+offset(2) | 4 | относительная |
| `SAV`   | 03 | opcode+reg+addr(4) | 6 | прямая |
| `SAVN`  | 04 | opcode+reg+offset(2) | 4 | относительная |
| `ADD`   | 05 | opcode+reg1+reg2 | 3 | регистровая (настройка не нужна) |
| `JUMP`  | 06 | opcode+addr(4) | 5 | прямая |
| `JUMPN` | 07 | opcode+offset(2) | 3 | относительная |
| `CALL`  | 08 | opcode+addr(4) | 5 | прямая |

Регистры: `R1..R4` (1 байт — номер). Смещение для относительной адресации —
`target - адрес_следующей_команды` (PC-relative), поэтому не требует настройки при
перемещении модуля целиком. ТКО-сетка в UI редактируемая (можно менять набор команд
без перекомпиляции — это удобно и для демонстрации, и для отладки).

### 3.2 Псевдокоманды

| Директива | Пример | Действие |
|---|---|---|
| `Start` | `Exampl Start 00001000` | имя программы + адрес загрузки по умолчанию (перекрывается полем UI) |
| `End`   | `End` | конец текста |
| `WORD`  | `One WORD 1` / `Rez WORD ?` | резерв 4 байта, опц. со значением; `?` — не инициализировано (не попадает в дамп кода) |
| `BYTE`  | `Text BYTE "Hello"` | строка → байты ASCII, без завершающего нуля |
| `EXTDEF`| `ExtName buf Str1` | (Этап 3) до 2 экспортируемых имён |
| `EXTREF`| `ExtRef Str2` | (Этап 3) 1–2 внешних (не определённых в модуле) имени |

### 3.3 Формат строки исходного текста

Фиксированные 4 столбца сетки — `Метка | Операция | Операнд1 | Операнд2`
(ровно как в сетке «Исходный текст» на скриншотах).

### 3.4 Ключевые структуры (Kotlin data classes)

```kotlin
data class OpcodeEntry(val mnemonic: String, val code: Int, val length: Int)

data class SourceLine(val label: String, val op: String, val operand1: String, val operand2: String)

data class SymbolTableEntry(val name: String, val address: Int, val isExternal: Boolean = false)

data class AuxTableRow(val address: Int, val opCode: Int?, val operand1: String, val operand2: String)

data class RelocationRow(val address: Int, val externalName: String? = null) // null = обычная (внутренняя) настройка

data class ExternalNameRow(val address: Int, val name: String) // экспортируемые (EXTDEF) имена

data class ObjectHeader(val name: String, val length: Int, val loadAddress: Int)

data class AssemblerError(val line: Int, val message: String)
```

### 3.5 Утилиты (аналог рекомендаций методички)

```kotlin
fun parseHex(text: String): Int = Integer.parseUnsignedInt(text.removePrefix("$"), 16)
fun toHex8(value: Int): String = "%08X".format(value)
fun namesEqual(a: String, b: String): Boolean = a.equals(b, ignoreCase = true) // аналог CompareText
```

## 5. Этап 1 — Простейший ассемблер (абсолютный формат)

### Шаг 1 — форма и данные (соответствует «Шаг 1» методички)
- [x] Сетка исходного текста — editable `StringGrid`, 4 столбца, предзагружен пример по умолчанию из `samples/Stage1Samples.kt` + запасные пустые строки для ручного ввода.
- [x] Поле адреса загрузки (`TextField`, hex, заполняется из выбранного примера, редактируемое).
- [x] Сетка ТКО — editable, предзаполнена набором из §3.1 (+ запасные строки).
- [x] Пустые изначально: вспом. таблица, ТСИ, список ошибок1, заголовок, список кода, ошибки2 (`resetResults()`, вызывается и при смене примера).

### Шаг 2 — логика первого прохода
`Pass1Engine.run(source, opcodes, loadAddress): Pass1Result(auxTable, symbolTable, errors)`

Алгоритм (классический проход 1):
1. `address = loadAddress` (из `Start`/поля ввода).
2. Для каждой строки:
   - если есть метка → проверить дубликат (ошибка «повторное определение имени `X`» если уже в ТСИ) → добавить в ТСИ на текущий `address`.
   - если `WORD`/`BYTE` → вычислить длину (4 либо длина строки), записать в аукс-таблицу «как есть» (директива, значение), `address += длина`.
   - если мнемоника есть в ТКО → записать в аукс-таблицу `(address, opCode, operand1, operand2)` без резолва символов, `address += length` из ТКО.
   - если мнемоника не найдена и это не директива → ошибка «неизвестная операция `X`».
3. По завершении — общая длина программы = `address - loadAddress`.
- [x] Реализовано в `engine/Pass1Engine.kt`, подключено к кнопке «Первый проход» (`MainApp.onFirstPass`): вызывает движок → заливает вспом. таблицу и ТСИ → если ошибок нет, разблокирует «Второй проход» (иначе оставляет заблокированной, выводит ошибки в список).
- [x] Проверено на 2 примерах в `samples/Stage1Samples.kt`, подключённых к `ComboBox`: `default` (без ошибок) и `withErrors` (дубликат метки `Loop` + неизвестная мнемоника `MOVE`). Покрыто тестами `Pass1EngineTest`.

### Шаг 3 — логика второго прохода
`Pass2Engine.run(auxTable, symbolTable, opcodes, loadAddress): Pass2Result(header, binaryLines, errors)`

1. Для каждой строки аукс-таблицы: если операнд — символическое имя, найти адрес в ТСИ (ошибка «не определено имя `X`», если отсутствует); если операнд — регистр/число, использовать как есть.
2. Сформировать байтовое представление команды по правилам ТКО (прямая → 4-байтный адрес; относительная → 2-байтное смещение `target - адрес_след._команды`; регистровая — как есть).
3. `WORD`: 4 байта значения (пропустить дамп, если `?`); `BYTE`: ASCII-байты строки.
4. Каждая строка объектного кода печатается в `Двоичный код` как строка hex-байт через пробел (одна строка источника → одна строка списка).
5. Заголовок: имя программы (из `Start`), длина программы (hex), адрес загрузки (hex).
- [x] Реализовано в `engine/Pass2Engine.kt`, подключено к кнопке «Второй проход» (`MainApp.onSecondPass`).
- [x] Проверено golden-тестом `Pass2EngineTest` — двоичный код и заголовок (`Exampl`, `0000002B`, `00001000`) побайтово совпадают с эталонным скриншотом методички (`docs/labs/img_4.jpg`); дополнительно проверена ошибка «не определено имя» для неразрешённого символа. Живой прогон через UI Automation (клик «Первый проход» → «Второй проход» на отдельном тестовом инстансе) подтвердил тот же результат в реальном приложении.

**Известное упрощение**: форма команды (регистр/адрес/смещение) жёстко привязана к
конкретной мнемонике (см. комментарий в `Pass2Engine`) — редактирование кодов и
длин в ТКО поддерживается, но не полностью произвольная замена набора команд.
Кнопка «Второй проход» не блокируется автоматически при последующей правке
исходного текста без повторного запуска «Первого прохода» — сознательное
упрощение для Этапа 1.

## 8. Сквозные UI-решения (замена рекомендаций методички под JavaFX)

| Delphi/`TStringGrid` | JavaFX-аналог |
|---|---|
| `ColCount`/`RowCount` | список `TableColumn`, `ObservableList` данных |
| `Options/goEditing = true` | `TableView.isEditable = true` + `cellFactory = TextFieldTableCell` только на сетках исходного текста и ТКО |
| `ScrollBars = ssNone`, `FixedRows/Cols = 0` | `TableView` без доп. настроек (полосы прокрутки скрывать через CSS при известной высоте, если нужно 1-в-1) |
| `DefaultRowHeight = 15` | CSS `.table-row-cell { -fx-cell-size: 15px; }` на сцену |
| `CompareText` | `String.equals(other, ignoreCase = true)` |
| `StrToInt('$'+s)` / `IntToHex(n,8)` | `parseHex(s)` / `toHex8(n)` (§3.5) |

## 9. Тестирование по этапам

- Движок (`engine/`) покрывается JUnit5-тестами независимо от UI:
  - `Pass1EngineTest` — корректная ТСИ/аукс-таблица, обнаружение дубликатов меток и неизвестных мнемоник.
  - `Pass2EngineTest` — побайтовое сравнение кода на фиксированных сэмплах (золотые примеры), ошибка «не определено имя».
  - `RelocationTest` (Этап 2) — таблица настройки для прямая/относительная/смешанный.
  - `ExternalLinkageTest` (Этап 3) — `EXTDEF`/`EXTREF`, корректность таблицы настройки с именами, содержимое «Внешние имена».
- UI проверяется вручную по каждому шагу — сверка с соответствующим скриншотом из `docs/labs/`.

## 11. Порядок работы

Строго по этапам 0 → 1 → 2 → 3, каждый со своим коммитом; внутри этапа — сначала
модель/движок + тесты, затем UI-проводка. Этап 2 и 3 **не переписывают**, а
расширяют движок и модели Этапа 1 (аддитивные изменения) — это прямо требуется
методичкой («изменить логику второго прохода», «расширить исходный текст»).
