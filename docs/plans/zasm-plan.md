# Zasm — визуализатор двух-/однопроходного ассемблера
## План реализации на Kotlin + JavaFX

Источник задания: `docs/labs/img.png`, `img_1.png` (текст методички) и `img_2.jpg…img_7.jpg`
(скриншоты примера-эталона «Zasm 1.0/2.0/3.0», Delphi, Зыкин А.А., гр. 4408, 1999 —
приведены методичкой **как иллюстрация UI/workflow**, а не как код для копирования;
конкретный набор команд и мелкие детали студент выбирает сам).

---

## 0. Что требуется по методичке (сжатая выжимка)

Программа моделирует работу двухпроходного ассемблера тремя нарастающими этапами:

| Этап | Формат объектного модуля | Ключевая новая способность |
|---|---|---|
| 1 | Абсолютный | Базовый проход 1 → ТСИ/вспом. таблица, проход 2 → бинарный код |
| 2 | Перемещаемый | Переключатель «только прямая» / «только относительная» адресация; таблица настройки для прямой |
| 3 | Полный перемещаемый (раздельное ассемблирование) | `EXTDEF`/`EXTREF`, внешние имена/ссылки, сохранение в файл |

Всегда одна форма с 3 панелями:

- **Левая**: исходный текст + ТКО (таблица кодов операций). В методичке исходный текст — сетка и есть поле адреса загрузки; у нас текст вводится в `TextArea`, а адрес начала задаётся операндом `START` (см. §5).
- **Средняя**: вспомогательная таблица (результат прохода 1) + ТСИ + список ошибок прохода 1.
- **Правая**: заголовок объектного модуля + список/сетка перемещений (появляется в Этапе 2) + внешние имена (Этап 3) + двоичный код + ошибки прохода 2 (+ кнопка «Сохранить…» в Этапе 3).

Кнопки «Первый проход» / «Второй проход» запускаются последовательно с блокировкой второй до успешного выполнения первой; выпадающий список «Выбор примера» переключает встроенные тестовые программы (в т.ч. с ошибками).

## 2. Архитектура

Чёткое разделение **движка** (чистый Kotlin, без зависимостей от JavaFX, легко тестируется) и **UI** (JavaFX, только отображение/события):

```
org.slavacom.zasm
├── model/          — доменные классы (Instruction, SourceLine, SymbolTableEntry, ...)
├── engine/         — Pass1Engine, Pass2Engine, AssemblerEngine, ErrorReporter
├── samples/        — встроенные тестовые программы (для ComboBox "Выбор примера")
├── io/             — сохранение объектного кода в текстовый файл (Этап 3)
└── ui/             — MainApp (Application), панели, table-адаптеры, контроллер
```

`AssemblerEngine` — единственная точка входа для UI: держит текущее состояние
(источник, ТКО, адрес загрузки) и по вызову `runPass1()` / `runPass2()` возвращает
неизменяемый результат (`Pass1Result` / `Pass2Result`) со всеми таблицами и списком ошибок.
UI только рендерит эти результаты в `TableView` — никакой бизнес-логики в контроллерах.

Это позволяет писать unit-тесты на движок (проверка каждого этапа методички —
«проверить работоспособность кода для нескольких примеров, в т.ч. при наличии ошибок»)
без запуска JavaFX.

## 3. Модель предметной области (общая для всех этапов)

Набор команд и директив отошёл от эталона Zasm (`LD/LDN/...`) к SIC-подобной
модели демонстрационной C#-версии лабораторной: формат команды определяется
**длиной** из ТКО, а тип адресации кодируется в младших 2 битах байта МКОП.

### 3.1 Таблица кодов операций (ТКО)

`model/OpcodeTable.kt`. ТКО по умолчанию (`DefaultOpcodeTable`):

| Команда | МКОП | Длина |
|---|---|---|
| `JMP`    | 01 | 4 |
| `LOADR1` | 02 | 4 |
| `LOADR2` | 03 | 4 |
| `ADD`    | 04 | 2 |
| `SAVER1` | 05 | 4 |
| `INT`    | 06 | 2 |

Формат команды по длине:

| Длина | Операнды | Кодирование |
|---|---|---|
| 1 | нет | `код*4` |
| 2 | число 0..255 **или** два регистра `R0..R15` | `код*4`, затем байт числа либо две hex-цифры регистров |
| 3 | метка | `код*4+тип`, адрес/смещение — 2 байта |
| 4 | метка | `код*4+тип`, адрес/смещение — 3 байта |

Тип адресации (младшие 2 бита МКОП): `0` — без адресации, `1` — прямая,
`2` — относительная (Этап 2). Поэтому МКОП в ТКО — не больше `3F`.

ТКО редактируется в UI (сетка с добавлением/удалением строк) и проверяется
`validateOpcodeTable`: пустые ячейки, размер полей (команда ≤ 6 символов, МКОП ≤ 2,
длина — 1 цифра), латиница/цифры, зарезервированные слова, МКОП ≤ `3F`,
длина 1..4, повторы команд и кодов.

### 3.2 Директивы

`model/Lexicon.kt` (`DIRECTIVES`, регистры, проверки лексем).

| Директива | Пример | Действие |
|---|---|---|
| `START` | `PROG START 100` | имя программы (≤ 10 символов) + адрес начала (hex) |
| `END`   | `END 100` | конец текста; операнд — точка входа (по умолчанию адрес начала) |
| `WORD`  | `B1 WORD 40` / `WORD ?` | 3 байта, десятичное значение ≤ `FFFFFF`; `?` — без кода |
| `BYTE`  | `BYTE 12` / `C"Hello!"` / `X"2F4C"` / `?` | 1 байт числа, символьная или 16-ричная строка |
| `RESB`  | `A1 RESB 10` | резерв N байт |
| `RESW`  | `A2 RESW 20` | резерв N слов по 3 байта |
| `EXTDEF`/`EXTREF` | | (Этап 3) |

### 3.3 Формат исходного текста

Исходный текст вводится в `TextArea` построчно: `[Метка] Операция [Операнд1] [Операнд2]`;
метка — если строка начинается без отступа (`model/SourceTextParser.kt`). Внутри
движка строка — `SourceLine(label, op, operand1, operand2)`. Метка — латинские
буквы и цифры, первая — буква; не совпадает с директивой, командой ТКО, регистром
и именем программы.

### 3.4 Ключевые структуры

```kotlin
data class OpcodeEntry(val mnemonic: String, val code: Int, val length: Int)
data class SourceLine(val label: String, val op: String, val operand1: String, val operand2: String)
data class SymbolTableEntry(val name: String, val address: Int)
data class AuxTableRow(val address: Int, val opText: String, val operand1: String, val operand2: String, val sourceLine: Int)
data class AssemblerError(val line: Int, val message: String)
data class Pass1Result(programName, startAddress, endAddress, entryPoint, auxTable, symbolTable, opcodes, errors, warnings)
data class Pass2Result(records: List<String>, errors: List<AssemblerError>)
```

Оба прохода **останавливаются на первой ошибке**. Результат прохода 1 хранит ТКО,
по которой он выполнен, — проход 2 работает только с ним (`AssemblerEngine`).

### 3.5 Утилиты (аналог рекомендаций методички)

`model/HexUtils.kt`: `parseHex` (строго hex-цифры, аналог `StrToInt('$'+s)`),
`parseDecimal`, `toHex6` (адрес — 3 байта, `MAX_ADDRESS = FFFFFF`), `toHex2`,
`toAsciiHex`. Сравнение имён без учёта регистра — `equals(ignoreCase = true)`
(аналог `CompareText`).

## 6. Этап 2 — Программа в перемещаемом формате (лаба 2)

Ключевое требование: программа ассемблируется в **одном из двух взаимоисключающих
режимов** — «ТОЛЬКО прямая адресация» или «ТОЛЬКО относительная адресация».
Режим выбирает пользователь; команда, использующая адресацию другого режима,
даёт ошибку. Смешанных программ нет.

**Сверка с методичкой** (`img.png`, `img_4.jpg`, `img_5.jpg`):
- методичка просит проверить три варианта — «только прямая», «только относительная»
  и «смешанный случай»; по требованию преподавателя вместо смешанного случая
  делается переключатель режимов (смешанная программа = ошибка в любом режиме);
- в эталоне Zasm 2.0 `Start` без операнда, адреса во вспом. таблице и ТСИ идут с
  `00000000`, в заголовке адрес загрузки `00000000` — подтверждает `START = 0`;
- таблица настройки хранит адреса **команд** с прямой адресацией (`00000000`,
  `00000006`, `0000000F`, `00000015` для `LD/LD/SAV/JUMP`), двоичный код не меняется
  по сравнению с абсолютным форматом, кроме базы 0;
- относительное смещение в эталоне — от адреса следующей команды, 2 байта
  (Этап 3: `SAVN R1 Rez` по адресу `0F`, длина 4 → `04 01 000D` = `20 − 13`);
- в эталоне относительная адресация задаётся отдельной мнемоникой (`LDN`, `SAVN`,
  `JUMPN`), у нас — синтаксисом операнда `[метка]` при той же мнемонике, т.к. тип
  адресации уже кодируется младшими битами МКОП.

Опирается на модель текущего движка (Этап 1): младшие 2 бита байта МКОП —
тип адресации (`код*4+0` — без адресации, `+1` — прямая, `+2` — относительная);
адресация бывает только у команд длиной 3/4 (операнд-метка). Команды длиной 1/2
и директивы режимом не затрагиваются.

### Шаг 1 — модель и синтаксис
- [ ] `model/AddressingMode.kt`: `enum class AddressingMode { DIRECT, RELATIVE }`
  (подписи для UI: «Только прямая адресация», «Только относительная адресация»).
- [ ] Синтаксис операнда команд длиной 3/4:
  - прямая — метка как есть: `LOADR1 B1`;
  - относительная — метка в квадратных скобках: `LOADR1 [B1]`
    (`[имя]` целиком, имя — допустимая метка; `SourceTextParser` такой токен
    уже читает как один операнд).
- [ ] `Pass1Engine.run(source, opcodes, mode: AddressingMode? = null)` —
  `null` означает абсолютный формат Этапа 1 (поведение и тесты Этапа 1 не
  меняются); `AssemblerEngine.runPass1(..., mode)`. Режим сохраняется в
  `Pass1Result.mode`, второй проход берёт его оттуда (как уже сделано с ТКО).

### Шаг 2 — логика прохода 1: контроль режима
- [ ] Для команды длиной 3/4 определить тип адресации операнда (скобки → относительная,
  иначе прямая) и сверить с режимом:
  - режим `DIRECT`, операнд `[X]` → ошибка «относительная адресация запрещена в режиме „только прямая адресация“»;
  - режим `RELATIVE`, операнд `X` → ошибка «прямая адресация запрещена в режиме „только относительная адресация“».
- [ ] Во вспомогательную таблицу пишется `код*4+1` (прямая) или `код*4+2`
  (относительная), операнд — имя метки без скобок.
- [ ] Перемещаемый формат: программа ассемблируется с адреса 0 — операнд `START`
  должен быть `0` (или пустым → 0); ненулевой адрес — ошибка «в перемещаемом
  формате адрес начала должен быть 0». Фактический адрес загрузки задаёт
  загрузчик, а не ассемблер.

### Шаг 3 — логика прохода 2: настройка и смещения
- [ ] Прямая адресация (`тип 1`): адрес метки из ТСИ, как в Этапе 1, **плюс** адрес
  команды добавляется в таблицу настройки (её адресное поле нужно корректировать
  при загрузке).
- [ ] Относительная адресация (`тип 2`): `offset = адрес_метки − адрес_следующей_команды`,
  кодируется в дополнительном коде на 2 байта (длина 3) или 3 байта (длина 4);
  выход за диапазон — ошибка «смещение до метки `X` не помещается в команду».
  В таблицу настройки такая команда НЕ попадает (позиционно-независима).
- [ ] Защита на втором проходе (на случай ручной правки вспом. таблицы/ТКО):
  тип адресации в байте МКОП, не совпадающий с режимом, — ошибка того же текста,
  что и в проходе 1.
- [ ] Объектный модуль: после `T`-записей — по записи `M  адрес_команды` на каждую
  строку таблицы настройки, затем `E`. В режиме `RELATIVE` `M`-записей нет.

### Шаг 4 — UI
- [ ] Окно становится Zasm 2.0 («…в перемещаемом формате»): все проходы из UI
  идут в одном из двух режимов, примеры — `Stage2Samples` (абсолютный формат
  остаётся в движке и тестах Этапа 1).
- [ ] Верхняя панель: переключатель режима — две `RadioButton` в одной `ToggleGroup`
  («Только прямая адресация» / «Только относительная адресация»), по умолчанию — прямая.
- [ ] Смена режима сбрасывает результаты (`invalidatePasses()`) и блокирует
  «Второй проход» — результат прохода 1 был получен в другом режиме.
- [ ] Правая панель: «Таблица настройки» (`ListView<String>`, адреса hex) над
  двоичным кодом; в режиме относительной адресации остаётся пустой.

## 8. Сквозные UI-решения (замена рекомендаций методички под JavaFX)

| Delphi/`TStringGrid` | JavaFX-аналог |
|---|---|

| `CompareText` | `String.equals(other, ignoreCase = true)` |
| `StrToInt('$'+s)` / `IntToHex(n,8)` | `parseHex(s)` / `toHex8(n)` (§3.5) |

## 11. Порядок работы

Строго по этапам 0 → 1 → 2 → 3, каждый со своим коммитом; внутри этапа — сначала
модель/движок + тесты, затем UI-проводка. Этап 2 и 3 **не переписывают**, а
расширяют движок и модели Этапа 1 (аддитивные изменения) — это прямо требуется
методичкой («изменить логику второго прохода», «расширить исходный текст»).
